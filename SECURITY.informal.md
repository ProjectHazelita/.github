# Security Policy

Thank you for helping keep Project Hazelita and its users safe.

If you discover a security vulnerability in a Project Hazelita project, please report it **privately** and avoid creating a public issue, discussion, pull request, or other public disclosure before the vulnerability has been reviewed.

## Reporting a vulnerability

Whenever available, please use the affected repository's **Private Vulnerability Reporting** or GitHub Security Advisory mechanism.

If the repository provides its own `SECURITY.md`, follow the reporting instructions there instead.

A useful vulnerability report may include:

- the affected repository, component, and version or commit;
- a description of the vulnerability;
- steps or proof of concept needed to reproduce it;
- the potential security impact;
- relevant logs, screenshots, or technical details;
- any mitigation or fix you have already identified.

You do not need to provide a complete exploit or proposed patch in order to report a vulnerability.

Please remove unrelated personal information, credentials, access tokens, private keys, and other secrets from reports whenever possible.

## What should be reported privately?

Please use a private security channel for issues that may allow an attacker to:

- execute unintended code or commands;
- bypass authentication or authorization;
- access, modify, or disclose data without permission;
- escalate privileges;
- obtain credentials, secrets, or cryptographic material;
- significantly disrupt the availability or integrity of a service;
- exploit another user through behavior they would not reasonably expect;
- otherwise compromise the confidentiality, integrity, or availability of a Project Hazelita project or its users.

If you are unsure whether an issue has security implications, reporting it privately first is welcome.

Ordinary bugs without meaningful security impact can be reported through the project's normal issue tracker.

## Coordinated disclosure

Please give maintainers a reasonable opportunity to investigate and address a reported vulnerability before publishing detailed information that could enable exploitation.

When practical, Project Hazelita maintainers will work with reporters to understand the issue, coordinate remediation, and determine an appropriate disclosure timeline.

The complexity and impact of vulnerabilities can vary significantly, so we do not promise a fixed response or remediation deadline in this organization-wide policy.

## Security research

Good-faith security research intended to improve the safety of Project Hazelita projects is welcome.

Please make reasonable efforts to:

- avoid accessing, modifying, or deleting data that does not belong to you;
- avoid degrading services or affecting other users;
- use the minimum level of access necessary to demonstrate an issue;
- stop testing if continued activity could cause harm;
- report discovered vulnerabilities through an appropriate private channel.

A vulnerability report should demonstrate the security issue without causing unnecessary impact.

## Public disclosure and fixes

Security fixes may be developed privately when early publication could expose users to unnecessary risk.

Once an issue has been sufficiently addressed, maintainers may publish an advisory describing the affected versions, impact, remediation, and appropriate acknowledgements.

Public disclosure decisions should prioritize the safety of affected users while respecting the contributions of security researchers.

## Scope

This policy serves as the default security policy for Project Hazelita repositories.

Individual projects may define additional requirements, supported versions, reporting channels, threat models, or disclosure procedures in their own `SECURITY.md`.

When a repository-specific security policy exists, that policy takes precedence.

---

Security works best when curiosity and responsibility travel together.

Thank you for choosing to report vulnerabilities in a way that gives everyone a better chance to fix them safely. 🪼
